# Docker 契约 / Docker contract

状态：**契约已定义 · 实现刻意缺席**（`deferred`）

`reusable-docker.yml` 的 preflight 检查本目录下是否存在 `Dockerfile`，
缺失时**明确失败**。这是刻意的，不是遗漏——原因见第 3 节。

---

## 1. 这会是什么

一个只包含**后台服务**（`cmd/proxyclient-service`）的最小镜像。
不是图形界面：容器里没有桌面环境，也没有意义。

```
proxyclient-service      后台服务二进制
cores/                   核心二进制（仅在版本已冻结时）
config/client-config.json  出厂配置模板
```

用户通过挂载的 IPC 套接字控制它，或让它按配置直接运行。

## 2. 安全约束

这些是**契约的一部分**，实现时必须满足：

| 约束 | 原因 |
|---|---|
| 运行用户**非 root** | 容器内的 root 配合挂载的宿主路径风险很高 |
| **不烘焙任何凭据** | 镜像层会被推送与缓存；凭据必须通过挂载或运行时环境传入 |
| 镜像内**不含面板地址** | 与源码规则一致：不预置任何生产地址 |
| 核心二进制**校验 SHA256 后**才入镜像 | 与桌面端同一条规则，见 `deploy/packaging/README.md` |
| TUN 能力**不承诺接管宿主网络** | 容器命名空间内的网络接管只影响容器自身 |
| 两个核心**不会同时运行** | 与其它客户端一致 |

## 3. 为什么现在刻意没有 Dockerfile

三条理由，按重要性排序：

**第一，Docker 目标在目标清单里是 `deferred: true` 且 `required: false`。**
它明确后置、不阻塞核心交付。现在实现它属于做计划外的事。

**第二，即使写了也无法验证。**
本机没有 Docker，也没有 Go 工具链。一个从未构建过的 Dockerfile
与没有 Dockerfile 的区别，只是「看起来完成了」——
而「看起来完成了」正是本项目一直在避免的东西。

**第三，更根本的是：镜像要跑起来，还需要一项尚未确定的设计。**
后台服务通过本地 IPC 被控制，而容器里的 IPC 套接字无法被宿主上的
图形界面直接访问。要让容器形态真正可用，必须先决定控制方式：

- 挂载套接字目录（宿主与容器共享路径）？
- 改用 TCP 环回 + 令牌？
- 还是让容器只按配置文件运行、不做交互控制？

这三个选项对安全性的影响完全不同——尤其第二个，
本地管理接口一旦监听到非环回地址，同网络的任何人都能控制它
（`platform/netmgr` 里对这一点有显式拒绝）。

**先写 Dockerfile 等于先选了一个方案，而那个选择还没有被论证过。**

## 4. 实现它需要什么

| 前置条件 | 现状 |
|---|---|
| 后台服务可执行文件 | **已完成**（`cmd/proxyclient-service`） |
| 核心版本锁定 | 未完成（`versions.lock.json` 仍是占位） |
| IPC 在容器中的控制方式 | **未决定**（见第 3 节） |
| 基础镜像的 32 位 / arm64 manifest 检查 | 未做 |
| 首次真实构建 | 未做 |

前三项里，第三项是设计问题而不是实现问题。

## 5. 实现时的工作流会做什么

`reusable-docker.yml` 的 build 作业已预留结构：

1. 按目标架构检查基础镜像 manifest
   （32 位与 arm64 必须**独立检查**，不能假设与 64 位等价）；
2. `buildx build` 产出 OCI 镜像；
3. **校验镜像架构与目标一致**——构建成功不代表架构正确，
   与 APK 的 ABI 校验同理；
4. 导出 OCI artifact（默认不推送）。

## 6. 三个目标

| 目标 | 平台 | 必需 |
|---|---|---|
| docker-amd64 | linux/amd64 | 否 |
| docker-386 | linux/386 | 否 |
| docker-arm64 | linux/arm64 | 否 |

`docker-386` 的注意事项：需独立检查基础镜像 manifest 与依赖，
不能假设所有镜像仓库都提供 32 位版本。
