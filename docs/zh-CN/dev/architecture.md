# 架构 / Architecture

面向：想读懂或修改本项目的人。读完应当能回答「某个改动该落在哪个目录」。

状态：设计已完整，**全部代码从未编译过**。本文描述的是设计意图，
不是已验证的行为。哪些部分已实测、哪些没有，见
[design/plan/STATUS.md](../../../design/plan/STATUS.md)。

## 1. 三个进程与三种客户端

```
┌─────────────────────┐        ┌──────────────────────┐
│  桌面 GUI（C++）     │        │  Android（Kotlin）    │
│  wxWidgets           │        │  Compose + VpnService │
└──────────┬──────────┘        └───────────┬──────────┘
           │ 本地 IPC（JSON）               │ 同进程（无 IPC）
           │ Unix socket / 命名管道          │
┌──────────▼──────────┐                    │
│  后台服务（Go）      │                    │
│  cmd/proxyclient-   │                    │
│  service            │                    │
└──────────┬──────────┘                    │
           │ 启动 / 停止                   │
┌──────────▼──────────┐        ┌───────────▼──────────┐
│  核心（外部二进制）  │        │  核心（外部二进制）    │
│  sing-box (external)│        │  sing-box (external) │
└─────────────────────┘        └──────────────────────┘
```

### 为什么桌面端必须分成两个进程

修改系统代理、启动核心、恢复网络这些操作需要在**界面崩溃或被强杀后**
仍然可被恢复。而界面恰恰是最容易崩的那一个。

更具体地说：Windows 上无法向普通进程发送优雅终止信号。如果网络接管由
GUI 进程负责，那么 GUI 被强杀后系统代理会**一直指着已经退出的本地端口**，
用户的表现是「浏览器打不开任何网页」，而他不知道该改哪里。

因此网络恢复必须由独立于界面生命周期的一方负责，并且要有**持久化日志**
（见下）。

Android 不需要 IPC：`VpnService` 与界面在同一进程模型内，
系统负责其生命周期。

## 2. 目录职责

```
src/versions/0.1.0/
├── deploy/
│   ├── packaging/          打包契约与核心获取脚本
│   └── targets/            目标清单（构建矩阵的唯一来源）
└── src/
    ├── cmd/                可执行入口
    │   └── proxyclient-service/
    ├── shared/             跨端共用的纯逻辑（无平台依赖）
    │   ├── panel/          面板 API 适配（登录、取订阅链接）
    │   ├── subscription/   订阅拉取与节点解析
    │   ├── domain/         标准节点模型
    │   ├── compiler/       sing-box 配置编译器
    │   ├── secrets/        凭据存储抽象与脱敏
    │   └── i18n/           文案加载、协商与格式化
    ├── runtime/            运行期编排
    │   ├── coordinator/    连接事务状态机
    │   ├── core/           核心进程生命周期
    │   ├── coreupdater/    核心下载、校验与更新
    │   └── ipc/            UI ⇄ 服务的本地协议
    ├── platform/           平台相关实现
    │   ├── netmgr/         网络接管适配层与后端
    │   ├── winproxy/       Windows 系统代理（注册表）
    │   └── journalfile/    持久化恢复日志
    └── apps/
        ├── desktop/        C++ GUI
        └── android/        Kotlin GUI
```

**分层规则：`shared` 不依赖 `runtime` 或 `platform`。**
违反它会让纯逻辑被迫携带平台包袱，也让单元测试必须准备平台环境。

## 3. 四个独立维度

设计基线要求这四个维度**互不耦合**。它们不是同一件事的四种说法：

| 维度 | 取值 | 含义 |
|---|---|---|
| 界面模式 | 简单 / 专业 | 只影响呈现，不影响行为 |
| 流量接入方式 | 系统代理 / PAC / TUN / 仅本地端口 | 流量如何进入核心 |
| 路由策略 | 规则 / 全局 / 直连 | 进入核心后如何分流 |
| Android 应用范围 | 全部 / 排除列表 | 哪些应用走代理 |

**界面模式**是唯一一个「切换后行为完全不变」的维度。两种模式共用同一份
配置与同一个节点库；若各持一份，很快就会出现「简单模式显示已连接、
专业模式显示未连接」。

## 4. 连接事务

一次「连接」不是一步操作，而是一个可能有五步失败的事务：

```
validating          编译配置并让核心做原生配置检查
      ↓
starting_core       启动核心进程，等待就绪
      ↓
preparing_network   写入系统网络设置（记录原值）
      ↓
connecting          确认可用
      ↓
running             完成
```

任何一步失败都会尝试回滚，并**在回滚前先把「原值 / 写入值 / 所有者」
写进恢复日志**。这份日志必须能在进程被强杀后被重新读取。

### 所有权校验：为什么恢复不能直接写回

恢复时逐个键比较**当前值**与**我们当初写入的值**：

- 相等 → 写回原值（原值不存在则删除该键）
- 不等 → 记入冲突并**跳过**

不等就说明用户或其它软件在这期间改过它。直接覆盖等于把别人的修改抹掉，
而用户不会知道是谁干的。

`coreupdater` 的 SHA256 校验、`netmgr` 的冲突报告、`coordinator` 的
`RecoveryError` 都遵循同一条原则：**不掩盖，不代用户做决定**。

## 5. 核心分发（ADR-0003）

核心**不编译**，只下载官方预构建二进制：

1. 每个产物由 `versions.lock.json` **同时锁定版本与 SHA256**；
2. 校验**先于**落盘（先放目标位置再校验，中间有一段「未校验但可用」的窗口）；
3. 校验失败删除临时文件并中止；
4. 替换用「先备份、再原子改名」，失败可回滚；
5. **锁文件未冻结时拒绝下载**——一个静默包含未校验核心的安装包，
   在用户看来和正常包完全一样，却不具备任何完整性保证。

## 6. 单内核与能力表

客户端**只使用 sing-box** 一个内核。这不是一开始的设计——
最初让用户在内核之间二选一，后来按
[ADR-0005](../../../design/adr/ADR-0005-单内核-sing-box.md) 收敛为单内核。

**为什么收敛**，一句话说清：要提供的选项（规则分流、规则集、DNS 覆写、
TUN、嗅探、分应用代理）在 sing-box 的配置里**都是一等公民**，
逐项都有直接对应的字段；而双内核意味着维护两张能力表
（**都**标记为未实测，因此比一张更不可信）、
同一条节点换内核可能消失、打包体积翻倍而用户只用其中一个。

sing-box 仍有一个需要记住的边界：

| | sing-box |
|---|---|
| `transport.type` 取值 | 只有 `http, ws, quic, grpc, httpupgrade` |
| xhttp / splitHTTP | **不支持**；按能力表拒绝该节点并说明原因 |
| h2 / http | 映射为 `http` |
| TCP 上的 HTTP 伪装头 | 不支持 |
| REALITY | 支持，且同时支持 uTLS 指纹 |

**「不支持」不等于「静默丢弃」。** 遇到编不出来的节点，
编译器在报告里写明是哪一项能力缺失，
而不是产出一个核心不认的配置——后者要到运行时才暴露，
而错误信息来自核心深处。

能力表在 `shared/compiler/capability.go` 里，并且**标记为
`verifiedAgainst: "unverified"`**——它来自对核心源码的阅读，不是对
锁定版本的实测。有测试专门断言这个标记存在，防止有人悄悄把它改成「已验证」。

如果一个能力表被误标为已验证，用户会看到一个「支持」的选项、
选中后核心拒绝启动，而错误信息来自核心深处，与真正的原因相距很远。

界面选项与内核字段的完整对应关系见
[design/architecture/ui-options.md](../../../design/architecture/ui-options.md)。

## 7. 本地 IPC

协议在 Go 与 C++ 中各实现一次（`runtime/ipc/protocol.go` 与
`apps/desktop/src/core/ipc_protocol.{hpp,cpp}`）。

**漂移不会响亮地失败**：典型表现是「服务端说成功但界面没反应」。
两种语言的编译器都抓不到，因此有专门的脚本直接对比两侧定义
（`tools/scripts/check-ipc-contract.ps1`）。

设计要点：

- 握手校验**线协议版本**与**载荷结构版本**，两者独立演进；
- 版本不匹配时**拒绝服务**，不做尽力解析——尽力解析会把「字段缺失」
  变成难以定位的运行时错误；
- 统一错误结构含 `messageKey`，界面据此本地化，不解析服务端文案；
- 事件带序号与丢弃计数，**本地丢弃数与服务端丢弃数分开统计**：
  只报一个数字无法判断「界面看到的是不是全部事件」；
- 桌面客户端的读取线程**绝不调用界面代码**，事件排队由界面线程轮询——
  跨线程调用 wxWidgets 会导致随机崩溃，且只在负载高时出现。

## 8. 凭据处理

原则：**凭据不出现在源码、日志、测试夹具与导出中。**

| 机制 | 位置 | 作用 |
|---|---|---|
| `secrets.Store` | `shared/secrets` | 平台安全存储抽象（DPAPI / Secret Service / Keystore） |
| `secrets.Scrubber` | 同上 | 清除核心日志与错误文本里的凭据 |
| `json.Redact` | 桌面端 | 输出 JSON 前递归替换敏感字段 |
| `RedactUrl` | 桌面端 | 订阅链接整条即凭据，只保留参数名 |
| 状态文件权限 0600 | `runtime/ipc` | 句柄文件含本地访问令牌 |

平台缺少安全存储时，`secrets` 返回**明确错误**，调用方**不得**降级为
明文保存。

## 9. 多语言

三个客户端**共用仓库根的 `locales/*.json`**。两份翻译文件必然漂移，
最后表现为同一个错误在不同平台上显示不同的话。

约定（见 [i18n-convention.md](../../../design/architecture/i18n-convention.md)）：

- 文案键 = `<包名>.<主题>`；字段路径与凭据键使用不同的前缀，
  使自动检查能可靠区分三者；
- 缺键返回**键名本身**而不是空串：界面会显示 `panel.unauthorized`，
  问题立刻可见；返回空串则会变成难以察觉的空白；
- 越界占位符**原样保留**，同样是为了让缺陷可见。

`tools/scripts/check-i18n-keys.ps1` 同时扫描 Go、C++ 与 Kotlin 三种源码。

## 10. 构建与验证

**本机没有任何编译工具链**（无 Go / C++ / JDK / Android SDK），
因此所有编译与测试都在 GitHub Actions 里进行。

| 工作流 | 触发 | 作用 |
|---|---|---|
| `ci.yml` | 推送 / PR / 手动 | 静态预检、格式、编译与测试（Linux/Windows）、桌面核心与 GUI、契约与翻译 |
| `verify-targets.yml` | 手动 | 交叉编译到全部目标架构 |
| `build-*.yml` | 手动 | 产出安装包（7 个入口） |

本机能做且已经做的检查，见
[verification.md](verification.md)。
